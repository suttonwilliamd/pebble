# PB-01: Pebble v2 format and protocol contract

Status: **frozen wire contract**. PB-01 introduced this specification and exact
byte goldens. [PB-03/PB-04](../store-v2.md) implement the guarded production
object/ref store and immutable paged file API using these same vectors. PB-05/06
add ingestion/local CLI; [PB-08](../store-v2.md#pb-08-explicit-verified-v1-migration)
adds explicit copy-to-new-destination migration. V2 server endpoints remain later work.
Changing these bytes or invariants requires an explicit contract revision and new
fixtures; do not silently reinterpret an existing format-2 object.

PB-10 explicitly extends tree modes with literal links (2/3), adds a required local
repository capability marker, and versions new worktree intents separately.
Every previously valid envelope and ID remains unchanged; only formerly invalid
modes 2/3 gain meaning. No object kind, hashing rule, file codec, migration or
network endpoint is added. Protocol negotiation vectors below remain unchanged.

## Implemented v1 versus the format-2 contract

The source of truth for shipped behavior is `internal/snapshot/object.go`,
`repository.go`, `transfer.go`, and `internal/syncproto/http.go`:

| Area | Implemented v1 | Proposed v2 below |
| --- | --- | --- |
| Address | lowercase SHA-256 of content only; kind not in hash | SHA-256 of typed, versioned envelope |
| Stored object | JSON with type, size, hash, base64 content | binary canonical envelope |
| File revision | whole-file blob, flat tree | immutable manifest root and chunk pages |
| Commit | JSON, one optional `parent`, embedded hash | ordered `parents[]`, no embedded self-hash |
| Tags | no supported tag workflow; refs validate `heads/` only | typed lightweight/annotated tags, including nested targets |
| Remote | `/v1/{refs,fetch,push}`, bundle version 1, 32 MiB/50,000 objects | separate negotiated format/protocol 2 |

`CreateIndex` currently writes an index field `version:2`; that is **not** this
repository format. Historical module/checklist documents describe aspirations,
not implemented v2 behavior. ROCK libraries and `internal/remote` are not the
production CLI snapshot/remote path.

## 1. Canonical primitives and bounds

All integers are fixed-width, **big-endian**, with no padding or varints.
`u8`, `u16`, `u32`, `u64` occupy 1, 2, 4, 8 bytes; `i64` is two's-complement signed.
A count is `u32`, followed by exactly that many elements; zero is a real empty
list, never null/omitted.
`text` is `u32 byte_length || UTF-8 bytes`, maximum 65,535 bytes. Invalid UTF-8,
surrogates, NUL and Unicode control characters U+0000..001F/U+007F..009F are
rejected, except LF and TAB in commit/tag messages. No Unicode normalization,
case-folding, BOM insertion, newline conversion, JSON, or locale transforms occur.
An object's string spelling is identity-significant, including empty messages.
Author/email must be nonempty; email is identity text, not a validated mailbox.
Timestamp = `seconds:i64 || nanoseconds:u32 || utc_offset:5 ASCII bytes`.
Seconds range -2^63..2^63-1; nanoseconds range 0..999,999,999. The instant is
seconds plus nonnegative nanoseconds since the Unix epoch: -0.5 seconds is
(-1, 500000000). Offset is exactly `[+-]HHMM`, HH=00..23, MM=00..59; it records
the original display offset, not an adjustment to the stored UTC instant.
`+0000` and `-0000` remain distinct identity-significant provenance spellings.
Pre-epoch dates, fractional seconds and non-UTC offsets are representable.

Every record is:

```
50 42 32 00  kind:u8  payload_length:u64  payload
 P  B  2 NUL
```

The 13-byte header is included in the address. Consume exactly one record:
truncation, trailing bytes, unknown kinds, wrong magic/version and oversized
payloads are errors. Chunk payload limit: 8,388,608 bytes (8 MiB). All other
payloads: 1,048,576 bytes (1 MiB). Check bounds before allocation or arithmetic;
aggregate lengths must not exceed 2^63-1. Compression, transport framing, caches,
and packs are outside this logical encoding and cannot change its address.

| Kind byte | Name | Addressable object? |
| --- | --- | --- |
| 01 | chunk | yes |
| 02 | manifest-page | yes |
| 03 | manifest | yes |
| 04 | tree | yes |
| 05 | commit | yes |
| 06 | tag | yes |
| 80 | offer | no; negotiation message |
| 81 | selection | no; negotiation message |
| 82 | ref-update | no; protocol message |

### Typed IDs

Text ID: `pv2:<kind-name>:sha256:<64 lowercase hex digits>`; no aliases,
uppercase, whitespace, abbreviated hashes, or bare v1 hashes. Example kind name:
`manifest-page`, not its numeric spelling. Digest = SHA-256(**entire envelope**).
Wire link: `kind:u8 || digest:32 bytes` (33 bytes); format/hash algorithm are
implicitly v2/SHA-256. A wire link to the wrong kind is invalid even if that
address exists. Unknown digest algorithms/kinds require a new negotiated format.
No object contains its own ID. Empty chunk and empty tree are distinct; equal
payloads in different kinds also have distinct addresses. Verify declared kind,
full length, address and content before accepting an object; existing corrupt
bytes must never be overwritten or treated as deduplication success.

## 2. Immutable file manifests

Payload schemas (field order is normative):

```
chunk         = raw file bytes (including zero bytes; empty chunk is legal)
manifest-page = count || (chunk_link || length:u64)*
manifest      = file_length:u64 || file_sha256:32 || count ||
                (manifest-page_link || page_length:u64)*
```

Page count: 1..1,024 chunk entries. Chunk entry length: 1..8 MiB, exactly the
linked raw chunk length; empty chunks cannot appear in manifests. A manifest has
0..16,384 pages, at most 16,777,216 chunk references. Every non-final page has
exactly 1,024 entries; the final page has 1..1,024. Splitting a partially filled
page to add another page is noncanonical. Zero-length file has no pages and the
SHA-256 of empty bytes. A nonempty file must have pages. Each page length is the
checked sum of its chunk lengths, root length is the checked sum of page lengths,
and checksum is SHA-256 of reconstructed raw bytes in page/chunk order.

Page position implies chunk order and file offset; there are no mutable `next`
pointers or path-keyed chunk maps. Duplicate chunk links and repeated full pages
are legal and represent repeated bytes, not duplicate-map errors. A changed
revision constructs a new immutable root and changed pages; unchanged pages and
chunks may be shared. Two trees may bind the same pathname to different roots
without altering either revision. Chunk boundaries/algorithm policy are not
frozen by PB-01; each root records its complete ordered sequence independently.
A consumer must verify all links, lengths and final checksum before treating the
file as valid. A syntactically valid record with absent dependencies is an
incomplete graph, never an empty file or a partially successful publication.

## 3. Trees, commits and tags

```
tree   = count || (path:text || mode:u8 || manifest_link)*
commit = tree_link || parent_count || commit_link* || author:text || email:text ||
         timestamp || message:text
tag    = name:text || target_link || tagger:text || email:text ||
         timestamp || message:text
```

Trees are flat file-path lists, maximum 10,000 entries, strictly increasing by
unsigned UTF-8 bytes; duplicates and file/descendant pairs (`a`, `a/b`) are
invalid. Paths: 1..4,096 bytes, relative `/` separators, no empty/`.`/`..`
components, backslash, colon, control character, or `.git`/`.pebble` component
(ASCII case-insensitive). Mode 0 = ordinary file, 1 = executable file.
PB-10 adds mode 2 = symbolic link and mode 3 = directory-hinted symbolic link;
all modes >=4 are invalid. The linked manifest contains the exact literal target
bytes, not target contents: 1..65,535 bytes, no NUL, no normalization or UTF-8
requirement. Absolute, relative, dangling, directory and looping targets do not
authorize traversal. Mode 3 preserves Windows directory-link identity without
probing the target; POSIX preserves an unobservable stored hint on later commits.
Windows likewise preserves unobservable historical executable metadata but
refuses materialization it cannot represent. Junctions/other reparse types are
not symbolic links in this contract.

On POSIX, literal target bytes are the `readlink` value, including non-UTF-8
bytes. On Windows they are the exact UTF-8 API-view **SubstituteName** target and
relative/full **Flags**, not the optional **PrintName** display label or a forensic
serialization of the reparse buffer. Accepted target spelling must unambiguously
preserve the native flag semantics; no additional Windows fields are stored.
Only recognized absolute NT drive/UNC/volume
namespace prefixes receive reversible API spelling; dot components, separators,
case and Unicode are never cleaned. Tag, flags, bounds/alignment and UTF-16 must
validate without truncation/replacement; native target/type/flag readback must agree.
See [MS-FSCC](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/b41f1cbf-10df-4a47-98d4-1c52a833d913).
There is no origin/dialect tag: ambiguous cross-host interpretation fails closed,
not by inventing provenance. POSIX capture/materialization refuses backslash or
Windows-drive target spellings; Windows refuses slash/POSIX-absolute, stateful
drive/root-relative, alternate-stream and unsupported NT spellings or invalid
UTF-8. Such preserved graphs remain readable/verifiable; these are host operation
limits, not new wire-invalid vectors or authority to rewrite history.

No empty directories, arbitrary permission bits, ownership, ACLs or timestamps
are represented. Different Unicode normalization forms remain distinct; a
checkout must refuse a graph it cannot safely represent on its filesystem,
including case/Unicode collisions, reserved names and path limits. Never rename
or drop history to fit a host.

`parents[]` has 0..64 distinct commit links. Empty = root; one = ordinary commit;
two or more = merge. Order is significant: index 0 is first parent. Never sort
parents. Validate all parents, not just first-parent ancestry. Commit DAGs must
be acyclic and complete before ref publication. Tree/commit links cannot target
a chunk, page, manifest, or tag. Walks must bound resources and detect cycles;
local policy limits may be stricter but may not reinterpret bytes.

References have namespaces `heads/` and `tags/`. Remaining slash-separated
components must be nonempty ASCII `[A-Za-z0-9._-]+`, not start/end with `.`, not
end with `.lock`, and contain no `.git`/`.pebble` component (case-insensitive).
Within a namespace reject ASCII-case-insensitive equality and file/descendant
collisions. Branch refs target commits. Lightweight tag refs may target any
native object kind (01..06); annotated tag refs target tag objects whose `name`
equals the ref suffix. Tag names use the same component grammar. An annotation's
typed target may be any native object kind, including another tag. Follow every
target with kind checking and cycle detection, not implicit commit peeling;
missing targets or cycles invalidate the graph. Annotation identity, timestamp
and message affect its ID. A tag of a file manifest refers to that immutable
file revision, not its pathname; tagging a chunk/page does not imply a file.
Published tags are create-only in protocol 2; moving/deleting a tag requires a
future explicit administrative protocol, not ordinary branch force-update.

This is **not yet full Git metadata compatibility**: signed/fractional dates and
typed/nested tag targets are representable, but arbitrary Git headers, encoding
declarations, non-UTF-8 identity/message bytes and original signature material
still require preservation. PB-32/PB-33 must define a separately negotiated,
versioned preservation representation for original Git object kind, exact
payload bytes and original ID, extra metadata and signature provenance before
claiming lossless import/export. Original bytes must remain recoverable without
reconstructing them from normalized native fields. Unsupported input must fail
closed until that representation exists; rejection alone does not fulfill
PB-32's losslessness requirement. Never flatten tags, strip headers/signatures
or round dates. A future schema extension cannot alter format-2 IDs.

PB-23 signatures must bind the exact canonical native envelope bytes (including
kind/version/length), never a reserialized display, transport compression or a
v1 hash. Signature records/algorithms and attachment layout are not frozen here
and require a separately versioned contract. Author/tagger/email are identity
claims, not proof of authentication or signing-key ownership. Original Git
signature bytes, their original signed payload and verification provenance must
remain distinct from any native Pebble signature; do not claim a native
signature preserves or authenticates a converted Git signature.

## 4. Version negotiation and protocol boundary

Protocol version and repository/object format version are **separate axes**.
The following schemas freeze negotiation and ref intent, not transfer scheduling:

```
offer      = format_count || format:u16* || protocol_count || protocol:u16* ||
             feature_count || feature:text*
selection  = format:u16 || protocol:u16 || feature_count || feature:text*
ref-update = name:text || expected_present:u8 || [expected_link] || target_link
```

Version lists have 1..16 nonzero entries in strictly increasing numeric order.
Feature lists have 0..32 nonempty ASCII `[a-z0-9-]+` entries sorted by byte order,
without duplicates. Offers describe supported capabilities. Selection features
are **required** capabilities; format 2 requires exactly `paged-manifests` and
`typed-ids` in this contract. Other required features, unoffered features,
unsupported selected versions, missing required features, or no mutually
supported version are hard failures before any object/ref writes. Select the
highest mutually supported format and protocol independently; PB-01 defines only
format 2/protocol 2. Do not infer support from HTTP status, client name or URLs.
Negotiation must be fresh for the session and tied to its authenticated peer.

Future protocol 2 uses separate `/v2/` routes and these canonical binary bodies
(`application/vnd.pebble.v2`); no route is added by PB-01. The authenticated peer
exchanges offers before selection; both verify selection against both offers.
No intersection = unsupported-version failure, no fallback write to v1. Transport
security/authentication must remain at least the current HTTPS/loopback + bearer
policy; this contract grants no new credentials or permissions. Incremental
transfer, resumable offsets, pack/index formats and endpoint/status enumeration
are later cards, not invented here. Object frames remain verifiable independently.

`expected_present` is exactly 0 (ref absent, create-only) or 1 (one typed expected
link follows). Target is never null: deletion is not part of this contract.
Branch updates require absent ref or an exact expected ID plus fast-forward
ancestry through **all** parents; retry with already-installed target succeeds
only after graph verification. Tags require expected_present=0. Under the writer
lock, verify current ref, complete graph, type and address integrity, then publish
atomically/durably; failures cannot acknowledge or expose a partial ref update.
Unreferenced verified objects may remain after a failed transfer; GC policy is
not specified. Ref intent fixtures prove schema/types, not a working CAS engine.

## 5. Migration and compatibility boundaries

- The current CLI uses format2 for its seven local flows; `/v1/` remains the only
  shipped network protocol and accepts legacy repositories only. PB-03's library
  initializer keeps its empty-directory contract; PB-06 adds explicit working-
  directory initialization without changing existing files or migrating metadata.
- Existing repositories may retain exact ASCII `pebble-format 2\n`; new
  repositories use exact ASCII `pebble-format 2\nrequires filesystem-v1\n`.
  Absence still means legacy v1; other/malformed markers fail closed.
  New code reads old valid histories without upgrade. Mode-2/3 publication via
  direct `Put`, tree construction or ref graph publication requires explicit
  capability enablement on an old-marker store. Pure ID construction is not
  enablement. `pebble enable-filesystem` uses the existing persistent worktree
  guard followed by the store writer guard, refuses pending recovery, verifies
  inventory/refs, then atomically/durably publishes only the marker. It never
  replaces/unlinks guards or rewrites objects/IDs/refs/working bytes.
  PB-09 persistent-guard writers (verified against baseline
  `61586df728b858f04d39775855a78f230bfeb7a9`) revalidate after locking; old open
  handles and pre-lock races cannot cross enablement. Earlier marker-only or
  noncooperating writers are not a supported concurrent protocol. Do not run them.
  New journals use version 2 even for regular-only transitions in old-marker
  roots; old PB-09 recovery rejects the version before replay. New code still
  recovers supported version-1 intent without conversion/deletion. Old binaries
  cannot open capability-marked roots. A marker alone never makes a store valid;
  adding a marker to v1 is not migration, and a capability is not an OS privilege.
- The [PB-08 migrator](../store-v2.md#pb-08-explicit-verified-v1-migration)
  is explicit, offline, copy-to-new-destination with the
  original kept intact and backed up. It must validate the source first, preserve
  names, raw bytes, executable bits, identity/message/time within representable
  bounds and parent order, rebuild typed objects bottom-up, and emit a v1->v2 ID
  map. V1's optional parent maps to `[]` or `[parent]`; its embedded self-hash is
  not copied. A v1 hash must never be relabeled as a v2 ID.
- Unsafe legacy paths, corruption, unrepresentable timestamps/metadata, missing
  objects or unknown fields with migration significance must stop migration
  with a diagnostic, not silently discard history. No in-place or dual-write
  bridge, downgrade writer or lossy migration is included.
- Remote v1 endpoints/bundles stay byte-compatible and reject v2. There is no
  mixed-format graph or cross-format ref. V2 migrations/peers must not publish
  until the complete destination graph verifies independently.

## 6. Local golden corpus and verification

`internal/formatcontract/testdata/v2.json` is the reviewable local publication.
Each vector has a name, explanatory note, exact lowercase `wire_hex`, a pinned
text ID for addressable records, expected error class (empty means valid), and
names of its direct fixture dependencies. Negotiation vectors also name the two
offers. This JSON is a fixture container, **not** a wire format. No clock, random
input, filesystem traversal order, newline conversion or external data is used.
A separate marker vector pins the repository marker's bytes. All file bytes
used here are synthetic. PB-02 owns larger format-agnostic corpora/faults and
benchmarks; none are copied here.

Run from the repository root:

```
go test ./internal/formatcontract -count=1
```

The test-only independent decoder verifies framing, bounds, field grammar,
canonical ordering, typed addresses, dependency closure, page partitioning,
lengths, raw whole-file checksums, ordered parents, annotation/ref types,
negotiation and marker boundaries. Goldens include empty/raw binary data,
identical payloads across types, 1,024/1,025 chunk boundaries, repeated pages,
two revisions of one path, root/merge commits, tag forms, UTF-8, and invalid
framing, types, lengths, checksums, ordering, paths, parents and versions.
This is an executable specification, **not** a reusable production parser, store,
network implementation, or proof of production v2 support. Later cards must
consume these same vectors in their real implementations.

### Small byte examples

Spaces below are visual separators only; the JSON corpus stores continuous hex.
The header is `magic | kind | payload length`; the remainder is exact payload.

| Vector | Exact bytes (hex) |
| --- | --- |
| `chunk-empty` | `50423200 01 0000000000000000` |
| `chunk-a` | `50423200 01 0000000000000001 41` |
| `tree-empty` | `50423200 04 0000000000000004 00000000` |

`chunk-a` has ID
`pv2:chunk:sha256:5e6017fb3f0cd4b9d16342bd284d2cd5864701c95ebdaae28199cfcfdbcb216e`.
Its raw file SHA-256 is instead
`559aead08264d5795d3909718cdd05abd49572e84fe55590eef31a88a08fdffd`:
file checksums do not hash an envelope.

Both revision trees contain exactly `asset.bin`, ordinary mode:

| Fixture pair | Exact file bytes | Length | Immutable manifest ID |
| --- | --- | --- | --- |
| `tree-old` / `manifest-old` | `41` | 1 | `pv2:manifest:sha256:b463bfe09da67fc6589c4b15731806948cf5602dc002921bb665bcc2cab0de59` |
| `tree-new` / `manifest-new` | `00ff0a0d80` | 5 | `pv2:manifest:sha256:2ff254753031a53c067e376f65847c95dd346e525eb1e0fa776b089711be9f79` |

The latter's raw file checksum is
`896a425d1fade64e368ccca61003182138e59b7050bca9a7ec8f4ca99646f9fb`.
Each root is 98 bytes; each tree is 64 bytes. Reconstructing revision 2 must not
append to or overwrite revision 1's chunk sequence. The invariant test resolves
both bindings independently. `page-full` pins exactly 1,024 repeated one-byte
chunk references; `manifest-1025` adds a one-entry final page, and
`manifest-repeated-page` reuses the same full page twice. The long repeated hex
is intentional and annotated in the corpus, not generated during tests.

`commit-merge` orders `[commit-new, commit-side]`;
`commit-merge-reversed` orders `[commit-side, commit-new]` and has a different ID.
Signed date vectors cover -2^63, -0.5 seconds, 2^63-1, maximum nanoseconds,
non-UTC offsets and distinct `+0000`/`-0000` spellings. Typed tag vectors cover
commit, tree, file manifest, chunk, page and nested tag targets; unknown kinds
still fail closed.

PB-01's checked corpus contains 185 wire vectors (111 valid, 74 invalid), plus
decoded identity/revision/order/date/tag invariant assertions. The focused check
passed using cached Go 1.21.13 (`windows/amd64`), with `GOTOOLCHAIN=local`,
`GOPROXY=off` and `GOSUMDB=off`; no downloads, live service or user data involved.
